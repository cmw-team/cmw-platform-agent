# Транскрибация и разбор встречи

## Результат

Для каждой обработанной встречи всегда подготовь два отдельных Markdown-файла:

1. структурированное summary;
2. полный транскрипт без сокращений и цензуры.

Не выбирай режим результата по формулировке пользователя. Даже если он просит
только summary или только транскрипт, создай оба файла.

Перед анализом загрузи
[references/output-template.md](references/output-template.md) через
`load_skill_reference`, передав аргументы:

```json
{
  "skill_name": "cmw-summarize-meeting",
  "reference_path": "output-template.md"
}
```

`reference_path` задаётся относительно папки `references`, поэтому не добавляй
к нему повторный префикс `references/`. Используй шаблон только для содержимого
summary: структуру файла полного транскрипта создаёт tool.

Не выполняй веб-поиск и не отправляй транскрипт в KB или MCP.

## Источники

Используй:

- аудио- или видеофайл из текущей UI-сессии; либо
- готовый полный транскрипт, явно вставленный пользователем в сообщение или уже
  присутствующий в контексте текущей сессии.

Если полный транскрипт уже дан текстом, не вызывай
`transcribe_uploaded_media`.

Не извлекай транскрипт из DOCX, PDF, изображения или другого документа. Попроси
приложить исходное аудио/видео либо вставить готовый текст.

Если нет ни записи, ни готового транскрипта, не вызывай tools и ответь:

> Прикрепите аудио- или видеофайл встречи, который необходимо разобрать.

## Определение связи между несколькими файлами

Если приложено больше одного медиафайла и пользователь уже явно указал, что это
разные разговоры или последовательные части одного разговора, не переспрашивай.

Если связь между файлами не указана, до любых вызовов tools уточни:

> Эти файлы относятся к одному разговору или к разным? Если это части одного
> разговора, укажите их порядок.

Не транскрибируй ни один файл до ответа.

Если это части одного разговора:

1. установи порядок из сообщения пользователя;
2. если порядок нельзя надёжно определить, уточни его до вызова tools;
3. транскрибируй каждый файл в этом порядке;
4. проанализируй части как единый разговор;
5. создай ровно одну пару файлов с общим summary и общим транскриптом.

Если это разные разговоры:

1. обрабатывай каждый файл независимо;
2. не смешивай факты между разговорами;
3. создай отдельную пару файлов для каждого разговора.

Если пользователь явно выбрал только один файл из нескольких, обработай только
его.

## Транскрибация медиа

Для каждого выбранного файла вызови `transcribe_uploaded_media`:

```json
{"source": "<точное исходное имя файла с расширением>"}
```

Передавай только точное имя из текущей UI-сессии. Не передавай путь, URL,
переименованное или придуманное имя.

Фактическую пригодность контейнера и кодека проверяет FFmpeg внутри tool. Если
вложение очевидно не является аудио или видео, не вызывай tool. Если тип
неочевиден, используй фактический результат tool.

Успешный результат содержит полный текст в `data.transcript`. Прочитай весь
транскрипт каждого файла. Не анализируй только начало, отдельные фрагменты или
пересказ.

Текущий tool не выполняет диаризацию. Порядок текста не устанавливает личность
говорящего и не является надёжной границей смены спикера.

Не показывай пользователю сырой JSON tool.

## Анализ

Работай только с фактами полного транскрипта:

1. Сформулируй все содержательные основные выводы без искусственного
   ограничения количества.
2. Сгруппируй разговор по смысловым темам, а не по последовательным репликам.
3. Для каждой темы укажи, что обсуждалось, какие потребности, ограничения и
   позиции были озвучены.
4. Отдельно зафиксируй только действительно принятые решения и договорённости.
5. Отдельно зафиксируй следующие шаги, ответственных и сроки.
6. Отдельно зафиксируй оставшиеся открытые вопросы и риски.

Не выдавай предложение, гипотезу или обсуждавшийся вариант за решение. Если
решений нет, используй `Решения не зафиксированы`.

Не придумывай ответственного или срок. Если сведения отсутствуют, используй
`Не указан`.

Не приписывай слова конкретному человеку без надёжно установленного имени или
роли. Используй нейтральные формулировки.

### Контроль решений и ответственных

Перед созданием summary отдельно проверь каждое решение и каждый следующий
шаг:

1. Назови решение только при явном согласовании, а не потому, что вариант
   подробно обсуждали или несколько участников его поддержали.
2. Укажи имя ответственного только когда в самом тексте действие прямо
   назначено этому человеку: например, `Максим подготовит таблицу`.
3. Не восстанавливай имя по `я`, `ты`, порядку фраз, упоминанию имени в соседней
   фразе, должности, владению интерфейсом или предполагаемой роли участника.
4. Если действие понятно, но исполнитель неоднозначен, сохрани действие,
   поставь `Не указан` и сформулируй его без угадывания направления передачи:
   например, `Совместно проверить интерфейс и согласовать его настройку`.
5. Не используй порядок фрагментов транскрипта как доказательство авторства.

Упоминание имени в разговоре само по себе не означает, что этот человек
говорит, согласился выполнить действие или назначен ответственным.

Не выполняй анализ эмоций, личности или тональности. Не добавляй таймкоды:
`transcribe_uploaded_media` их не возвращает.

В summary убирай слова-паразиты, повторы и ненормативную лексику, если они не
влияют на смысл. Полный транскрипт не исправляй, не цензурируй, не сокращай и не
пересказывай.

## Создание файлов

### Одна встреча из одного медиафайла

После анализа последовательно вызови `save_meeting_markdown` дважды.

Сначала создай summary:

```json
{
  "artifact_type": "summary",
  "source_names": ["<точное имя файла>"],
  "content": "<полное summary по шаблону>"
}
```

Затем создай полный транскрипт из сессионного кэша. Не копируй полный текст в
аргументы tool:

```json
{
  "artifact_type": "transcript",
  "source_names": ["<точное имя файла>"],
  "content": null
}
```

Результат: `<основа-имени>_summary.md` и
`<основа-имени>_transcript.md`.

### Одна встреча из нескольких частей

В обоих вызовах передавай одинаковый список `source_names` в подтверждённом
порядке. В summary передай единый анализ всех частей. Для transcript передай
`content: null`: tool сам загрузит точные тексты всех частей из сессионного
кэша и сохранит их в подтверждённом порядке.

Результат: `combined_meeting_summary.md` и
`combined_meeting_transcript.md`.

### Несколько разных встреч

Для каждого файла независимо создай summary и transcript по схеме одной
встречи. Не передавай несколько разных разговоров одним списком
`source_names`.

### Готовый транскрипт из сообщения

Не вызывай `transcribe_uploaded_media`. Создай summary:

```json
{
  "artifact_type": "summary",
  "source_names": [],
  "content": "<полное summary по шаблону>"
}
```

Затем создай transcript:

```json
{
  "artifact_type": "transcript",
  "source_names": [],
  "content": "<полный исходный текст пользователя без изменений>"
}
```

Результат: `meeting_summary.md` и `meeting_transcript.md`.

Не утверждай, что обработка завершена, пока оба файла каждой встречи не
созданы успешно.

## Обработка ошибок

При ошибке не выдумывай содержание встречи и не маскируй ошибку готовым
summary.

Ошибки `transcribe_uploaded_media`:

- `file_not_found` или `invalid_source` — попроси приложить файл заново и
  использовать точное имя;
- `invalid_media` — сообщи, что файл не распознан как поддерживаемое аудио или
  видео;
- `audio_stream_not_found` — сообщи, что в записи нет аудиодорожки;
- `ffmpeg_not_found` — сообщи, что на сервере недоступен FFmpeg;
- `polza_api_key_missing` — сообщи, что на сервере не настроена переменная
  `POLZA_API_KEY`;
- `polza_authentication_failed` — сообщи, что Polza отклонила настроенный
  серверный ключ;
- `polza_insufficient_funds` — сообщи о недостатке средств;
- остальные ошибки — кратко передай безопасное сообщение tool и предложи
  повторить попытку.

Ошибки `save_meeting_markdown`:

- `transcript_not_cached` — повторно вызови `transcribe_uploaded_media` для
  указанного файла, затем повтори сохранение transcript;
- остальные ошибки — сообщи, какой файл не удалось подготовить, и не объявляй
  весь результат успешным.

Не показывай stack trace, физические пути, API key, Base64, внутренние
исключения или полный HTTP-запрос.

## Финальный ответ

После успешной подготовки всех файлов выведи в чат только короткое
подтверждение и имена готовых файлов. Не дублируй summary, транскрипт, JSON,
стоимость, токены или техническую статистику.

Пример:

> Обработка завершена. Подготовлены файлы:
> `client-call_summary.md`, `client-call_transcript.md`.

Если исходный запрос включает следующую задачу для другого skill, сначала
подготовь оба файла, затем используй полный результат
`transcribe_uploaded_media` из контекста как вход следующего skill. Не заменяй
его summary и не подменяй формат результата следующего skill.

## Конфиденциальность

- Не отправляй транскрипт в веб-поиск, KB или MCP.
- Не извлекай из разговора персональные данные для внешнего поиска.
- Не повторяй чувствительные данные в summary без необходимости.
- Передавай аудио во внешний сервис только через
  `transcribe_uploaded_media`.

## Проверка

- Обработан весь транскрипт каждого выбранного файла.
- Для нескольких вложений связь и порядок подтверждены до вызова tools.
- Для разных разговоров данные не смешаны.
- Summary соответствует шаблону и не ограничено фиксированным числом выводов.
- Решения, ответственные, сроки, участники и таймкоды не выдуманы.
- При отсутствии атрибуции спикеров имена не восстановлены из местоимений,
  порядка фрагментов текста или косвенного контекста.
- Для каждой встречи созданы summary и полный transcript.
- В transcript не потерян и не переписан исходный текст.
- Финальный ответ не дублирует содержимое файлов.
- Ошибки tools не скрыты выдуманным результатом.
