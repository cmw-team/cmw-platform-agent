# Адаптация продуктовой презентации под лида

## Назначение

Подготовить для маркетинга мини-ТЗ по адаптации продуктовой презентации
Comindware под конкретного лида. Итог — структурированный документ
с точными номерами и названиями слайдов, который маркетинг может взять
в работу.

Этот skill **не редактирует PPTX**, **не загружает файлы**, **не отправляет
презентацию во внешние сервисы**, **не обращается к модели** и
**не использует OCR или визуальный анализ изображений**. Факты берёт
из результата `extract_presentation_slides`; решения принимает сам.

## Обязательные материалы

Перед составлением мини-ТЗ загрузи точный шаблон и инварианты итогового
документа:

```json
{
  "skill_name": "cmw-plan-sales-presentation",
  "reference_path": "output-template.md"
}
```

`reference_path` задаётся относительно папки `references`, поэтому не добавляй
к нему повторный префикс `references/`.

Перед анализом содержимого обязательно вызови
`extract_presentation_slides` и полностью прочитай его результат.

## Доступные входные данные

Извлеки из сообщения пользователя, вложений и контекста диалога всё,
что присутствует:

- название компании;
- отрасль;
- описание проекта или сделки;
- потребности лида;
- боли и текущие ограничения;
- ожидаемый результат;
- сроки, бюджет и другие ограничения;
- участники со стороны клиента и их роли;
- текст брифа, если приложен;
- текст транскрипта разговора, если приложен;
- имена приложенных PPTX (точные исходные имена, под которыми они
  загружены в текущей сессии).

Не требуй все поля одновременно. Используй то, что есть, и явно
помечай источник каждого факта при сомнениях.

## Развилки по источнику презентации

Сначала проверь, достаточно ли понятны потребности лида по правилам
раздела «Развилки по контексту лида». Если требуется уточнение,
задай его **до вызова любого presentation tool**. После ответа
продолжай по порядку ниже:

1. **Одна приложенная пользовательская PPTX**. Вызови:

   ```json
   {"source": "<точное исходное имя>.pptx"}
   ```

2. **Ни одной PPTX не приложено**. Вызови:

   ```json
   {"source": "default-product-deck"}
   ```

3. **Приложено несколько PPTX**. Задай один уточняющий вопрос,
   какой файл является основной продуктовой презентацией, и
   **не начинай анализ до ответа**. Не пытайся определить основную
   презентацию по имени файла или до чтения её содержимого.

4. **Нужна библиотека кейсов**. Всегда вызывай дополнительно:

   ```json
   {"source": "default-case-library"}
   ```

5. **Tool вернул ошибку**. Не выдумывай содержание презентации.
   Объясни проблему кратко и попроси корректный источник. Не начинай
   итоговое мини-ТЗ на основе догадок.

Имя файла в `source` всегда передавай **как строку**, без путей:
точное исходное имя с расширением `.pptx` для пользовательского файла;
`default-product-deck` или `default-case-library` для дефолтных источников.

## Развилки по контексту лида

Если потребности лида понятны из брифа, транскрипта или сообщения —
не задавай лишних уточнений.

Задай ровно один уточняющий вопрос до вызова tool и итогового мини-ТЗ,
если
выполняется хотя бы одно из:

- отсутствуют и бриф, и транскрипт, и любое описание потребностей;
- приложено несколько PPTX и не указано, какая из них основная;
- компания или проект критично неоднозначны (например, имя совпадает
  с несколькими известными организациями и без уточнения нельзя
  выбрать релевантный кейс);
- входные данные содержат противоречие, меняющее рекомендации.

Не блокируй работу из-за отсутствия второстепенных данных
(точных сроков, бюджета, ролей участников). Эти поля влияют на
формулировки, но не отменяют анализ.

Если одновременно не хватает описания потребностей и не выбрана
основная из нескольких PPTX, объедини оба пункта в один короткий
уточняющий вопрос. После ответа не переспрашивай уже известное.

## База знаний Comindware

KB-инструменты подключаются через MCP. Фактический список tools может
меняться между сессиями; **перед любым утверждением о возможностях
платформы проверь фактический список доступных KB tools** в текущей
сессии. Рассматривай MCP как единственный источник знаний о платформе
Comindware; не подменяй его веб-поиском и не опирайся на память модели.

**Основной KB-tool:** `get_knowledge_base_articles`. Это инструмент,
который возвращает исходные статьи базы знаний с `kb_id`, названием,
URL и полным текстом. Используй его как **главный источник истины**
о возможностях Comindware Platform: именно его результаты подтверждают
или опровергают утверждение в новом слайде.

Когда вызывать:

1. Если рекомендация по презентации содержит решение или возможность
   платформы, которую необходимо подтвердить статьями KB, — вызови
   `get_knowledge_base_articles` с узким запросом.
2. Перед каждым платформенным утверждением проверь, что
   `get_knowledge_base_articles` доступен в текущей сессии. Если
   да — опирайся на возвращённые статьи.
3. Не используй `ask_comindware` для технического подтверждения
   возможностей платформы: он возвращает синтезированный ответ, а
   не исходные статьи. Если `ask_comindware` появляется в списке
   MCP tools, рассматривай его как запасной канал для общих вопросов
   и **не используй** вместо `get_knowledge_base_articles` в тех
   проверках, от которых зависит утверждение о платформе.
4. Если `get_knowledge_base_articles` недоступен или возвращает
   пустой результат по релевантному запросу, не обещай возможность
   платформы; обозначай предложение как **гипотезу для дополнительной
   проверки** (пометка «гипотеза для согласования» в поле
   `Основание` нового слайда).
5. Не изменяй `config/mcp_servers.yaml` в рамках этого skill.

Правила работы с результатом `get_knowledge_base_articles`:

1. Цитируй `kb_id` и название статьи в поле `Основание` нового
   слайда, чтобы маркетинг мог проверить источник.
2. Если статья не подтверждает утверждение, не включай его в
   новый слайд.
3. Если несколько статей противоречат друг другу, не выбирай
   одну «по умолчанию»; сформулируй контент как гипотезу и
   перечисли расхождения в `Основание`.

## Веб-поиск

Используй доступный tool `web_search`, если для персонализации презентации
не хватает публичного контекста о компании или требуется подтвердить её
официальный сайт и направление деятельности. Не делай поиск обязательным,
если бриф, транскрипт или сообщение уже дают достаточный контекст.

1. Сформируй один узкий запрос только из доступных публичных идентификаторов:
   названия компании, ИНН, корпоративного домена и, при необходимости,
   отрасли. Поиск по одному названию компании допустим.
2. Вызови tool в точном формате:

   ```json
   {"query": "<доступные идентификаторы> официальный сайт деятельность"}
   ```

3. По `data.results` сопоставь поля `title`, `url` и `content` с известными
   идентификаторами и определи вероятный официальный сайт. Если компания
   неоднозначна, разрешён один дополнительный уточняющий вызов `web_search`
   либо один вопрос пользователю.
4. Используй найденные сведения только для понимания публичной деятельности
   компании, отраслевого контекста и терминологии.
5. Если `web_search` вернул `success: false`, продолжай с имеющимися данными
   либо задай уточнение, если без идентификации компании нельзя выбрать
   релевантные слайды.

Не отправляй в запрос транскрипт, внутренние CRM-комментарии, персональные
данные, бюджет или непубличные условия сделки. Не используй веб-поиск как
доказательство возможностей Comindware Platform: такие утверждения проверяй
только по KB. Не заменяй веб-поиском полный анализ презентации.

## Алгоритм анализа

Выполни последовательно:

1. Составь внутреннюю рабочую карточку лида:
   компания, отрасль, проект, потребности, боли, ожидаемый
   результат, ограничения, участники, сроки. Эта карточка нужна
   для внутренней работы и **не показывается** в итоговом ответе.
2. Полностью прочитай результат `extract_presentation_slides` для
   основной презентации.
3. Полностью прочитай результат `extract_presentation_slides` для
   `default-case-library`, если он доступен.
4. Для каждого исходного слайда оцени связь с потребностями лида.
5. Классифицируй каждый исходный слайд **ровно в одну** из групп:
   `Оставить` или `Убрать`.
6. Оставляй слайд, если он:
   - объясняет релевантную проблему;
   - подтверждает нужную возможность;
   - показывает релевантный кейс;
   - нужен для логичной связности презентации.
7. Убирай слайд, если он:
   - не связан с запросом;
   - дублирует другой слайд;
   - слишком детален для встречи;
   - уводит разговор в нерелевантное направление.
8. Предложи **0, 1, 2 или 3 новых слайда**, которых действительно не
     хватает для проекта лида. **Не предлагай новые слайды просто
     для того, чтобы выполнить этот пункт** — если существующая
     презентация полно и точно покрывает потребности лида, верни
     `0` новых слайдов и явно зафиксируй это в разделе `Добавить`.
     Для каждого предложенного нового слайда укажи:
     - место вставки (после какого существующего слайда и почему);
     - название;
     - цель слайда;
     - ключевые тезисы (3–5 пунктов);
     - связь с потребностью лида;
     - основание (пункт из `default-case-library` или подтверждённая
       KB-цитата, если используется платформенное утверждение; иначе —
       пометка «гипотеза для согласования»).
9. Предложи **0, 1, 2 или 3 простые контентные правки** существующих
     слайдов. **Не предлагай правки ради выполнения этого пункта** —
     если ни один существующий слайд не нуждается в точечной
     корректировке формулировки, верни `0` правок и явно зафиксируй
     это в разделе `Контентные правки`. Каждая правка: какую фразу
     или блок заменить и на что. Правки не должны менять смысл
     слайда.
10. Собери итоговый порядок слайдов.
11. Перепроверь все номера и названия по результату
    `extract_presentation_slides`. Номера и названия должны совпадать
    с payload tool **в точности**.

## Строгий формат результата

Перед финальным ответом **обязательно загрузи** `output-template.md` через
`load_skill_reference` с `reference_path: "output-template.md"` и следуй ему
без отступлений. Шаблон определяет:

- точные заголовки разделов;
- инварианты итогового документа;
- правила для слайдов без заголовка;
- запрет на полный сырой dump текста презентации;
- запрет на утверждение, что skill уже изменил PPTX.

Если исходный слайд не имеет заголовка, в разделах `Оставить` /
`Убрать` используй текст `[без заголовка]` и сохрани его точный номер.

## Что этот skill не делает

- Не редактирует PPTX и не создаёт новые файлы.
- Не использует OCR и не анализирует визуальное содержимое
  изображений.
- Не обращается к внешним LLM, кроме родительского LangChain-агента.
- Не отправляет презентацию во внешние сервисы.
- Не обещает возможности платформы без KB-подтверждения.
- Не подменяет анализ веб-поиском.
- Не выполняет CRM-поиск и не запрашивает данные лидов из CRM.
- Не наследует логику скилла `cmw-prepare-lead-questions` и не
  заменяет его.

## Конфиденциальность

- Не отправляй в KB или веб-поиск: транскрипт целиком, внутренние
  CRM-комментарии, бюджет, непубличные условия сделки, персональные
  данные участников.
- Для KB используй только описание возможности платформы и
  контекстный пункт, по которому проверяешь утверждение.
- Если транскрипт или бриф содержит чувствительные данные, перед
  запросом в KB оставь только необходимый технический фрагмент.
