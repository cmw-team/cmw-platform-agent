# Мини-ТЗ по адаптации презентации — шаблон

Точный шаблон мини-ТЗ, который skill `cmw-plan-sales-presentation`
обязан вернуть в финальном ответе. Каждый раздел обязателен.
Содержимое разделов должно опираться на результат
`extract_presentation_slides` и доступную KB.

Разделы `Оставить`, `Убрать`, `Добавить`, `Контентные правки`,
`Итоговый порядок` присутствуют в документе **всегда**. Если
содержимое раздела пустое (например, `0` новых слайдов или `0`
правок), в теле раздела стоит явная пометка об этом, чтобы
маркетинг видел осознанное решение skill, а не пропуск.

## Структура

```markdown
# Мини-ТЗ по адаптации презентации

## Контекст

Компания: ...
Запрос/проект: ...
Основная презентация: ...

## Оставить

- Слайд 2 — «Давайте познакомимся». Причина: ... (обязательное поле,
  см. инвариант 1a)

## Убрать

- Слайд 11 — «...». Причина: ... (обязательное поле,
  см. инвариант 1a)

## Добавить

Выбери ровно один из двух вариантов ниже — они взаимоисключающие.
Никогда не выводи пометку «не требуется» вместе с блоками «Новый
слайд N» в одном ответе.

Вариант A (0 новых слайдов):

_«Новых слайдов не требуется — существующая презентация
покрывает запрос.»_

Вариант B (1–3 новых слайда, без варианта A):

### Новый слайд 1 — «...»

Место: после слайда N «...».
Цель: ...
Содержание:
- ...
- ...
- ...
Основание: ...

### Новый слайд 2 — «...»
...

## Контентные правки

_Если правок не требуется, раздел остаётся и содержит явную
пометку:_
_«Правок не требуется — формулировки существующих слайдов
соответствуют запросу.»_

- Слайд N — «...». Изменить: ...

## Итоговый порядок

1 → 2 → [Новый слайд 1] → 3 → ...
```

## Инварианты

Финальный документ обязан удовлетворять всем пунктам ниже. Перед
ответом проверь каждый пункт.

1. **Полнота покрытия.** Каждый существующий слайд основной презентации
   встречается **ровно один раз** в одном из разделов `Оставить` или
   `Убрать`. Ни один слайд не пропущен и не продублирован.

1a. **Обоснование решения.** Каждая запись в `Оставить` и `Убрать`
    содержит краткую `Причина: ...` (одно предложение), объясняющую
    решение через связь с потребностью лида, а не общую формулировку
    вроде «релевантно» или «не подходит» без конкретики.

2. **Номера.** Номера существующих слайдов в разделах `Оставить`,
   `Убрать`, `Контентные правки` и `Итоговый порядок` совпадают с
   номерами в payload `extract_presentation_slides` **в точности**.
   Не перенумеровывай.

3. **Названия.** Названия существующих слайдов в разделах `Оставить`,
   `Убрать` и `Контентные правки` совпадают с названиями из payload
   `extract_presentation_slides`. Если в payload название пустое,
   используй `[без заголовка]` (см. ниже).

4. **Новые слайды.** Предложено **0, 1, 2 или 3** новых слайда.
   `0` — допустимое значение: если существующая презентация полно
   и точно покрывает потребности лида, новые слайды не нужны.
   **Не предлагай новые слайды только для того, чтобы выполнить
   этот пункт.** У каждого предложенного нового слайда указаны:
   место вставки, название, цель, содержание (3–5 пунктов), связь
   с потребностью лида, основание. Если новых слайдов нет, раздел
   `Добавить` остаётся в документе с явной пометкой «Новых слайдов
   не требуется — существующая презентация покрывает запрос».

5. **Контентные правки.** Предложено **0, 1, 2 или 3** простые
   контентные правки существующих слайдов. `0` — допустимое
   значение: если ни один существующий слайд не нуждается в точечной
   корректировке формулировки, правки не нужны. **Не предлагай
   правки только для того, чтобы выполнить этот пункт.** Каждая
   правка указывает номер и название слайда и формулирует, что
   именно заменить. Если правок нет, раздел `Контентные правки`
   остаётся в документе с явной пометкой «Правок не требуется —
   формулировки существующих слайдов соответствуют запросу».

6. **Итоговый порядок.** Итоговый порядок:
   - не теряет ни одного слайда из `Оставить`;
   - не содержит ни одного слайда из `Убрать`;
   - отмечает новые слайды как `[Новый слайд 1]`, `[Новый слайд 2]`,
     `[Новый слайд 3]` в порядке их вставки;
   - согласован с разделами `Оставить`, `Убрать`, `Добавить`,
     `Контентные правки`.

7. **Без платформенных обещаний.** Ни одно утверждение о возможностях
   Comindware Platform не включено в новый слайд без KB-подтверждения
   или ссылки на релевантный пункт `default-case-library`. Если
   подтверждения нет, контент нового слайда формулируется как
   потребность, целевой процесс или гипотеза для согласования.

8. **Без сырого dump.** Полный текст презентации или большой фрагмент
   `slides[].text` не включаются в итоговый документ. Цитируются
   только номера, названия и краткие формулировки.

9. **Без ложных утверждений.** Skill **не заявляет**, что PPTX уже
   изменён, что файл сохранён, что маркетинг автоматически получит
   задачу, или что-либо подобное. Итог — текстовое мини-ТЗ.

10. **Тон и формат.** Раздел `Контекст` без избыточных подробностей
    о компании: только то, что нужно для понимания запроса. Разделы
    `Оставить`, `Убрать`, `Добавить`, `Контентные правки` —
    маркированные списки. `Итоговый порядок` — нумерованный список
    или цепочка `→`.

## Слайды без заголовка

Если в payload `extract_presentation_slides` для слайда `title == ""`,
в разделах `Оставить`, `Убрать`, `Контентные правки` и
`Итоговый порядок` используй текст `[без заголовка]` и сохрани
точный номер слайда. Не придумывай названия.

Пример:

```markdown
- Слайд 7 — [без заголовка]. Причина: единственный график без подписи;
  не относится к запросу лида.
```

## Что запрещено в финальном ответе

- ссылки на внутренние системные имена атрибутов Comindware
  (например, `cmw_contract_status`) в видимой части документа;
- обещания интеграций, которые не подтверждены KB или кейсами;
- обсуждение цены, скидок, условий сделки;
- упоминание того, что skill «уже изменил» или «уже создал» файл;
- текст полных слайдов из `slides[].text`;
- вольные переводы заголовков (например, перевод с русского на
  английский, если в payload заголовок был на русском);
- удаление или скрытие `default-case-library` из рассмотрения
  без явного указания причины.

## Чек-лист перед ответом

Перед отправкой мини-ТЗ пройди по чек-листу. Если хотя бы один пункт
не выполнен, исправь документ и только потом отвечай.

- [ ] Каждый существующий слайд упомянут ровно один раз
      в `Оставить` или `Убрать`.
- [ ] Каждая запись `Оставить`/`Убрать` содержит конкретную `Причина`,
      привязанную к потребности лида (не общую формулировку).
- [ ] Номера и названия совпадают с payload `extract_presentation_slides`.
- [ ] Раздел `Добавить` содержит **либо** пометку «не требуется»,
      **либо** блоки «Новый слайд N» — никогда оба варианта сразу.
- [ ] Новых слайдов 0, 1, 2 или 3; если 0, в разделе `Добавить`
      стоит явная пометка; если 1–3, у каждого есть место, название,
      цель, содержание, связь, основание.
- [ ] Контентных правок 0, 1, 2 или 3; если 0, в разделе
      `Контентные правки` стоит явная пометка; если 1–3, каждая
      правка указывает номер и название слайда и формулирует замену.
- [ ] **Новых слайдов и правок не больше, чем реально нужно.** Ни
      один пункт не добавлен только ради выполнения чек-листа.
- [ ] Итоговый порядок согласован с разделами выше.
- [ ] Нет утверждений о возможностях платформы без KB-подтверждения.
- [ ] Нет полного сырого dump текста презентации.
- [ ] Нет ложного утверждения, что PPTX уже изменён.
- [ ] Слайды без заголовка помечены `[без заголовка]`.
- [ ] Конфиденциальные данные не утекли в KB или веб-поиск.
