# Подготовка квалификационных вопросов по лиду

## Цель

Подготовь для сейла 10 открытых квалификационных вопросов, которые:

- соответствуют компании, отрасли и запросу лида;
- не повторяют уже известные ответы;
- помогают подтвердить проблему, последствия, ожидаемый результат и основания
  для продолжения пресейла;
- используют терминологию компании и отрасли умеренно и только при достаточных
  основаниях.

Не превращай вопросы в техническое обследование и не проектируй детальное
решение. Это этап прояснения боли и потребности.

## Обязательные материалы

Перед составлением вопросов вызови `load_skill_reference` отдельно для каждого
обязательного файла:

```json
{"skill_name": "cmw-prepare-lead-questions", "reference_path": "brief-short.md"}
```

```json
{"skill_name": "cmw-prepare-lead-questions", "reference_path": "question-bank.md"}
```

```json
{"skill_name": "cmw-prepare-lead-questions", "reference_path": "output-example.md"}
```

При использовании KB или веб-поиска дополнительно загрузи соответствующую
инструкцию:

```json
{"skill_name": "cmw-prepare-lead-questions", "reference_path": "knowledge-base-search.md"}
```

```json
{"skill_name": "cmw-prepare-lead-questions", "reference_path": "web-research.md"}
```

`reference_path` задаётся относительно папки `references`: никогда не добавляй
к нему префикс `references/` повторно.

Пользователь не обязан прикладывать брифы: используй встроенные references.

## Доступные входные данные

Извлеки всё, что присутствует:

- ID лида;
- email, только если пользователь явно передал его в текущем сообщении или вложенных данных;
- название компании;
- корпоративный домен, извлечённый из email пользователя;
- отрасль;
- текст запроса лида;
- дополнительные комментарии сейла;
- транскрипт разговора или встречи.

Не требуй все поля одновременно.

## Получение данных CRM

### Если есть ID лида

Используй `get_record_values`. Значения каждого вызова находятся по пути
`data[record_id][attribute_alias]`. Передавай ID в параметре `record_ids`
списком, даже если ID один. `null` для любого атрибута — нормальный
результат: не считай его ошибкой и не выдумывай значение.

Выполни последовательность:

1. Сначала прочитай карточку лида:

   ```json
   {
     "record_ids": ["<ID лида>"],
     "attribute_system_names": ["Area", "Zaprosy", "Kompaniya", "INN"]
   }
   ```

2. Если `Area` содержит непустой ID, вызови tool ещё раз:

   ```json
   {
     "record_ids": ["<ID из Area>"],
     "attribute_system_names": ["TitleCalc"]
   }
   ```

   Используй `TitleCalc` как название отрасли или направления, только если
   значение действительно получено.

3. Если `Zaprosy` содержит один или несколько непустых ID, передай все такие
   ID одним вызовом:

   ```json
   {
     "record_ids": ["<первый ID из Zaprosy>", "<следующий ID из Zaprosy>"],
     "attribute_system_names": ["Opisaniezaprosa"]
   }
   ```

   Используй полученные `Opisaniezaprosa` как текст запроса лида. Если значений
   несколько, объедини только непустые описания без повторов.

4. Используй `Kompaniya` как название компании и `INN` как ИНН, только если
   соответствующие значения не `null` и не пустые.

### Контрольная точка после CRM

Если первый вызов успешен, но **все четыре** атрибута `Area`, `Zaprosy`,
`Kompaniya` и `INN` вернули `null` или пустое значение, не продолжай
анализ и не выдавай итоговые 10 вопросов. Сообщи пользователю, что по указанному
ID не получены данные, и попроси проверить ID, передать запрос лида прямо в чат
или предоставить другой ID. Используй смысловую формулировку:

> По данному ID не найдено данных: Area, Zaprosy, Kompaniya и INN пусты.
> Проверьте корректность ID. Введите запрос лида в чат либо предоставьте другой
> ID лида.

Если заполнен хотя бы один из четырёх атрибутов, не считай карточку автоматически
достаточной. Сопоставь CRM-данные с уже переданными сообщением и транскриптом:

- если нигде нет текста запроса лида, попроси описать запрос;
- если нигде нет названия компании и ИНН, попроси назвать компанию или
  предоставить ИНН;
- если отсутствуют и запрос, и идентификатор компании, задай один объединённый
  вопрос о них обоих.

Например, если из CRM получены только `Area` и `TitleCalc`, но отсутствуют
`Kompaniya`, `INN` и `Opisaniezaprosa`, попроси пользователя указать запрос
лида и название компании либо ИНН. Не спрашивай повторно то, что уже получено
из CRM, сообщения или транскрипта.

### Если нет ID, но пользователь передал email

Используй email только если пользователь явно передал его в текущем сообщении
или вложенных данных. Не запрашивай `Email` из CRM и не ищи карточку CRM по
email.

Извлеки домен. Корпоративный домен используй только для идентификации компании
в веб-поиске. Не используй личные почтовые домены для определения компании.

Если компания и запрос уже понятны, не блокируй подготовку вопросов.

Если данных недостаточно, попроси ID лида либо название компании и запрос.

### Если нет ID и email не передан

Если компания и запрос уже понятны, не блокируй подготовку вопросов.

Если данных недостаточно, попроси ID, email либо название компании и запрос.
Уточнение задаётся до итоговой десятки и не является частью результата.

## Приоритет источников

При противоречиях используй следующий приоритет:

1. уточнение пользователя в текущем диалоге;
2. прямые слова клиента из транскрипта;
3. данные карточки CRM;
4. официальный сайт компании;
5. надёжные внешние источники;
6. отраслевые гипотезы.

Отделяй подтверждённые сведения от предположений. Не встраивай предположение
в вопрос как установленный факт.

## Веб-поиск компании

Используй веб-поиск для идентификации компании и изучения её деятельности,
если ранее получен хотя бы один идентификатор:

- непустой `INN` из CRM;
- корпоративный домен, извлечённый только из email, явно переданного пользователем;
- название компании из CRM, сообщения или транскрипта.

Если не получены ни ИНН, ни корпоративный домен, ни название компании, не
пытайся идентифицировать компанию веб-поиском. Используй другие доступные
данные или запроси нужное уточнение по правилам skill.

Если tool `web_search` доступен и есть хотя бы один идентификатор, действуй по
порядку:

1. Используй ИНН как основной идентификатор; корпоративный домен — как запасной.
   Не используй личные почтовые домены.
2. Если название компании уже известно, включи его в поисковый запрос вместе с
   ИНН или доменом. Если доступны только название компании, ищи по нему.
3. Вызови `web_search` с одним узким запросом по форме:

   ```json
   {"query": "<доступные идентификаторы> официальный сайт"}
   ```

4. По `data.results` найди официальный сайт, сопоставляя `title`, `url` и
   `content` с доступными идентификаторами. Если официальный сайт неоднозначен,
   разрешён один дополнительный уточняющий вызов `web_search`.
5. Ознакомься с общедоступным описанием деятельности по найденным результатам.
6. Используй сведения о деятельности только как контекст для персонализации
   вопросов.

Не делай вывод о компании только по совпадению названия в поисковой выдаче.
Если поиск по одному названию даёт несколько правдоподобных компаний и не
удаётся подтвердить официальный сайт, задай уточняющий вопрос.
При расхождении с данными CRM, сообщения или транскрипта следуй порядку
приоритетов источников выше.

## Рабочий процесс

### Шаг 1. Нормализуй контекст

Собери рабочую карточку:

```text
Компания:
ИНН:
Домен:
Отрасль:
Запрос:
Известные ответы:
Неясности:
```

Эта карточка нужна для внутренней работы. Не показывай её в итоговом ответе.

### Шаг 2. Определи, достаточно ли данных

Попробуй восстановить компанию и запрос из сообщения, CRM и транскрипта.

Задай уточняющий вопрос, если:

- компанию невозможно однозначно определить;
- запрос отсутствует во всех источниках;
- найдено несколько подходящих компаний;
- источники содержат критичное противоречие.

Не задавай уточнение, если оно лишь слегка улучшит формулировки и без него
можно подготовить полезные вопросы.

### Шаг 3. Извлеки известные ответы

Отметь темы, которые уже подтверждены:

- контекст инициативы;
- текущий способ работы;
- конкретная проблема;
- последствия;
- предыдущие попытки;
- ожидаемый результат;
- критерии успеха;
- срочность и срок;
- владелец задачи, инициатор и ЛПР;
- бюджет, ограничения и риски;
- ожидаемый следующий шаг.

Не задавай вопрос повторно только ради заполнения формального списка.
Допускается уточняющий вопрос, если известный ответ неполный, противоречивый
или требует измеримого критерия.

### Шаг 4. Исследуй компанию

Сначала загрузи `web-research.md` через `load_skill_reference` с
`reference_path: "web-research.md"`, затем вызови `web_search` по его правилам.

Ищи только сведения, которые помогают:

- понять деятельность и отраслевую терминологию;
- проверить идентичность компании;
- понять вероятный контекст запроса;
- сделать вопросы конкретнее, не превращая гипотезы в факты.

### Шаг 5. При необходимости проверь базу знаний

Сначала загрузи `knowledge-base-search.md` через `load_skill_reference` с
`reference_path: "knowledge-base-search.md"`, затем используй
`get_knowledge_base_articles` по его правилам,
если запрос содержит платформенные, процессные или интеграционные требования,
и знание документации поможет задать более содержательный вопрос.

База знаний не нужна для каждого лида. В этом skill она помогает сформулировать
вопросы, но не должна превращать результат в презентацию возможностей продукта.

### Шаг 6. Возьми короткий бриф за основу

Начни с 10 вопросов из `brief-short.md`.

Для каждого вопроса проверь:

1. Есть ли уже достоверный ответ?
2. Подходит ли вопрос к запросу лида?
3. Продвигает ли вопрос квалификацию сделки?
4. Не дублирует ли он другой вопрос?

### Шаг 7. Замени слабые вопросы

Если ответ уже известен, вопрос неприменим или малоценен:

1. Найди в `question-bank.md` вопрос по той же теме.
2. Если вся тема уже закрыта, выбери вопрос по наиболее важному незакрытому
   полю квалификации.
3. Не используй банк как источник для механического добора количества.
4. Не создавай два вопроса, запрашивающих одну и ту же информацию.

### Шаг 8. Адаптируй формулировки

Используй название компании и отраслевую терминологию умеренно.

Хорошая адаптация:

> Как сейчас руководство видит задолженность по странам, юрлицам и покупателям?

Плохая адаптация:

> Как ваша инновационная международная логистическая экосистема FlexWay
> осуществляет end-to-end visibility дебиторской задолженности?

Не перегружай вопрос названиями продуктов и профессиональным жаргоном.

## Контракт результата

Верни:

- ровно 10 вопросов;
- один вопрос на строку;
- без заголовка;
- без вступления;
- без нумерации и маркеров;
- без пояснений, источников и заключения;
- каждый вопрос должен заканчиваться знаком `?`.

Перед ответом проверь:

- вопросов ровно 10;
- нет смысловых дублей;
- нет вопросов с уже известным полным ответом;
- вопросы открытые, а не предполагающие ответ «да/нет»;
- нет неподтверждённых фактов;
- терминология используется умеренно;
- вопросы подходят для живого разговора, а не для чтения анкеты.

## Конфиденциальность

Не отправляй в веб-поиск:

- внутренние комментарии CRM;
- транскрипт целиком;
- личные email и телефоны;
- бюджет и непубличные детали сделки;
- персональные данные участников.

Для веб-поиска используй только название компании, ИНН, корпоративный домен,
отрасль и общедоступное описание направления деятельности.
